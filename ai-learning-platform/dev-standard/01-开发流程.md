# 开发流程规范

> 从需求到交付的完整闭环：需求拆解 → 阶段开发 → 三层测试 → 文档归档 → 仓库同步。

## 一、需求接收与拆解

收到需求（无论大小）后，第一步是**拆解为可跟踪的开发要点**，产出拆解表：

| # | 要点 | 实现方式 |
|---|------|----------|
| 1 | 用户提出的功能 A | 后端：xxx；前端：xxx |
| 2 | 用户提出的约束 B | 配置/权限/适配处理方式 |

同时用 todo 工具建立任务清单（每要点一条，标注优先级），随开发推进即时更新状态——**完成一项勾一项，不攒批**。

拆解原则：
- 一个要点应在一个可测试的范围内（能被一条测试用例验证）；
- 后端接口、前端页面、数据库变更分开列；
- 用户口头提到的隐含期望（如"不要显示 ID"）也要沉淀为显式要点。

## 二、阶段化开发

### 2.1 阶段划分

项目按阶段推进，每阶段 1~3 个主题，产出可运行的增量版本。参考节奏：

| 阶段 | 主题 | 产出 |
|------|------|------|
| 一 | 环境搭建与基础骨架 | 工程初始化、登录鉴权、数据库连通 |
| 二 | 核心业务主流程 | 最主要的领域模型与 CRUD |
| 三 | 扩展业务模块 | 依赖主流程的次级模块 |
| 四 | 亮点功能 | AI 等差异化能力 |
| 五~六 | 运营与数据 | 积分/活动/统计分析 |
| 七 | 功能与接口测试 | 全量测试 + Bug 修复 |
| 八+ | 深度优化 | 性能、状态机、资源本地化等 |

### 2.2 单个功能的开发顺序

1. **数据库**：改 `sql/init.sql`（表结构 + 初始数据），本地执行；
2. **后端**：entity → mapper → service（含鉴权/事务）→ controller → （必要时）VO/DTO；
3. **前端**：api 封装 → 页面/组件 → 路由 → 菜单；
4. **联调**：浏览器实测走通完整用户路径。

## 三、三层测试体系

### 3.1 接口测试

- 工具：Python 脚本（`tests/api_test.py`，requests 库）或 curl；
- 覆盖：正常路径 + 权限边界（学生访问教师接口应 403、教师越权他人资源应被拒）+ 参数边界；
- 登录态：先登录拿 token，后续请求带 `Authorization: Bearer <token>`；
- 造数：测试数据用 SQL 直插（测试后清理），避免污染业务数据。

### 3.2 浏览器测试

- 使用浏览器自动化走真实用户路径：登录 → 目标页面 → 操作 → 断言界面结果；
- 验收标准看**用户视角**：列表显示什么、按钮点了发生什么、有无红色报错；
- 移动端适配至少做逻辑验证（断点切换、布局切换代码审查）。

### 3.3 回归测试

任何后端改动（重新打包）后，对受影响模块做回归：

- 之前的接口用例重跑；
- 重点关注：改 A 是否坏 B（如新增过滤器是否影响文件上传、改序列化是否影响旧参数格式）；
- 回归通过才允许同步仓库。

## 四、文档规范

每阶段结束（测试通过后）产出《阶段N技术报告-主题.md》放入 `docs/`，固定结构：

```markdown
# 阶段N技术报告：<主题>
> 日期 / 范围 / 目标

## 一、任务背景与要点拆解        ← 需求拆解表
## 二~N、各功能实现方案           ← 含关键代码片段、设计取舍
## N+1、数据库变更               ← 建表/改表 SQL + 初始数据
## N+2、回归测试                 ← 接口测试表 + 浏览器测试表（全部列出结果）
## N+3、遗留说明                 ← 已知问题、外部依赖、边界情况
## N+4、本阶段新增/修改文件清单   ← 按工程分组，标注关键改动
```

文档纪律：
- 报告写"为什么这样设计"而不只是"改了什么"；
- Bug 修复要记录**现象 → 排查过程 → 根因 → 修复方案**（这是最有价值的部分）；
- 文档随代码同步进仓库，不落本地。

## 五、仓库同步

### 5.1 同步脚本 sync.sh

```bash
#!/bin/bash
set -e
REPO=/path/to/local/repo          # 本地仓库（GitHub 项目目录）
cd "$REPO"

# 文档与原型
mkdir -p <project>/docs <project>/prototype
cp -f /workspace/docs/*.md <project>/docs/ 2>/dev/null || true

# 代码工程：排除依赖与构建产物
EXCLUDES="--exclude=node_modules --exclude=target --exclude=dist --exclude=.m2 --exclude=*.log"
rsync -a --delete $EXCLUDES /workspace/backend/ <project>/backend/ || true
rsync -a --delete $EXCLUDES /workspace/admin-web/ <project>/admin-web/ || true

# 有变更才提交推送
if [ -n "$(git status --porcelain)" ]; then
  git add <project>
  git -c user.name="<name>" -c user.email="<email>" \
    commit -m "自动更新：同步项目代码与文档 $(date '+%Y-%m-%d %H:%M')" >/dev/null
  git push origin main
fi
```

要点：
- `rsync --delete` 保持仓库与工作区一致，排除 `node_modules`/`target`/`dist`；
- commit message 统一格式：`自动更新：同步项目代码与文档 <时间>`；
- 无变更不产生空提交。

### 5.2 定时同步

配置每小时自动执行 sync.sh 的定时任务，保证工作区与远端不脱节；重要节点（阶段完成）仍手动触发确认。

## 六、环境与运维纪律

| 事项 | 规范 |
|------|------|
| 后端启动 | 从 `backend/` 目录启动 jar（静态资源相对路径依赖工作目录） |
| 数据库 | 建表/初始数据统一进 `sql/init.sql`；演示数据单独文件 |
| 出网代理 | 沙箱/受限环境给 JVM 加 `-Dhttp(s).proxyHost/Port`；HTTP 客户端启用系统代理感知 |
| 端口规划 | 后端 8080，管理端 5174，用户端 5173，互不冲突 |
| 日志排障 | 后端日志重定向到文件；先看日志再下结论，不要凭猜测改代码 |

## 七、Bug 修复标准动作

1. **复现**：用最小步骤稳定复现；
2. **定位**：区分前端 / 代理 / 网关 / 后端（看请求是否到达后端日志是关键手段）；
3. **根因**：写清楚为什么会发生（如"代理对 query string 预解码一次导致中文被拒"）；
4. **修复**：最小改动 + 兼容新旧两种路径；
5. **回归**：确认修复不破坏其他场景（直连/代理、ASCII/中文、普通请求/上传）；
6. **记录**：写入当阶段报告的 Bug 修复章节。
