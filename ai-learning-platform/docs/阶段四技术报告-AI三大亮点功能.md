# 阶段四技术报告：AI 三大亮点功能

> 本报告记录阶段四 AI 答疑、AI 出题、AI 批改三大亮点功能的技术选型与实现细节，是毕业答辩的核心亮点章节，也是面试复盘的重点材料。

---

## 1. 本阶段功能回顾

| 功能 | 使用者 | 核心能力 |
|------|--------|---------|
| AI 智能答疑 | 学生 | 多轮对话、课程上下文、SSE 流式打字机输出、会话管理 |
| AI 智能出题 | 教师 | 按课程/章节/知识点/题型生成题目草稿，审核后入库 |
| AI 智能批改 | 教师 | 简答题评分（0-10）+ 批改建议，可采纳/改分，总分自动重算 |

## 2. 大模型接入：智谱 GLM + OpenAI 兼容协议

### 怎么使用
- 调用智谱开放平台 `https://open.bigmodel.cn/api/paas/v4/chat/completions`，该接口与 OpenAI Chat Completions 协议完全兼容（请求体 `model/messages/stream`，响应 `choices[0].message.content`）；
- 使用 Spring WebFlux 的 `WebClient` 作为 HTTP 客户端，流式场景用 `bodyToFlux(ServerSentEvent.class)` 直接消费上游 SSE；
- 配置全部走 `application.yml` + 环境变量：`ai.zhipu.api-key: ${ZHIPU_API_KEY:}`，**密钥绝不硬编码进代码库**。

### 为什么这样选
- **为什么选智谱 GLM**：国产大模型对中文教育场景效果好，`glm-4-flash` 免费额度充足、响应快，适合毕业设计演示；平台提供 OpenAI 兼容接口，未来换任何兼容模型（DeepSeek、Moonshot）只需改 base-url 和 model。
- **为什么用 WebClient 而不是 RestTemplate**：RestTemplate 是阻塞式客户端，无法消费 SSE 流；WebClient 基于 Reactor 天然支持响应式流，是 Spring 官方推荐的现代 HTTP 客户端。

### 规避的问题
- 大模型响应体可能很大，默认 256KB 内存缓冲会溢出，显式配置 `maxInMemorySize(4MB)`；
- 流式调用设置 60 秒 `timeout`、非流式 90 秒，防止大模型无响应时线程被无限挂起。

### 面试问答
**Q：为什么不用 Spring AI 框架而自己封装客户端？**
A：Spring AI 封装了统一抽象，但本项目只用一个大模型、两种调用模式（流式/非流式），直接用 WebClient 调 OpenAI 兼容协议代码更少、可控性更强，也更能体现对 HTTP 协议与响应式编程的理解。若未来接入多模型再引入 Spring AI 抽象层也不迟——这是"按需引入、避免过度设计"的取舍。

> **演进说明（阶段九已迁移）**：随着 AI 功能稳定（答疑/出题/批改/文章四大场景），本阶段已按上述预留路径迁移至 Spring AI 官方 `spring-ai-starter-model-openai` **通用协议模块**（不使用厂商绑定 starter），保留全部现有能力与接口签名。迁移细节见《阶段九技术报告-课程驳回状态机与SpringAI迁移及全链路回归测试》。

## 3. SSE 流式输出：AI 答疑的打字机效果

### 怎么使用
- **后端**：Controller 返回 `Flux<String>`，`produces = text/event-stream`，Spring 自动把每个元素编码为一个 SSE 事件（`data: xxx\n\n`）；
- **链路**：学生提问 → 保存用户消息 → 组装多轮历史 → `ZhipuAiClient.chatStream()` 返回上游文本块流 → 逐块透传给前端，同时 `doOnNext` 聚合全文、`doOnComplete` 落库完整回答；
- **首帧协议**：流的第一个元素是 `[SESSION:{id}]`，把新建会话的 ID 下发给前端（后续消息要挂到该会话）；
- **前端**：用 `fetch` + `ReadableStream.getReader()` 手动解析 SSE（axios 不支持流式读取），按 `\n\n` 切事件、按 `data:` 取内容，逐块追加到气泡并滚动到底部，配合闪烁光标实现打字机效果。

### 解决什么问题
- 大模型生成一段回答要 3~10 秒，若等全部生成完再返回，用户面对长时间空白会以为卡死；SSE 让第一个字在 1 秒内出现，**体验从"等待"变成"观看"**；
- 流式完成后才落库，保证数据库里存的是完整回答而非半截内容。

### 为什么用 SSE 而不是 WebSocket
| 维度 | SSE | WebSocket |
|------|-----|-----------|
| 通信方向 | 服务端→客户端单向 | 双向 |
| 协议 | 基于 HTTP，天然穿透代理 | 独立协议，部分网关需额外配置 |
| 断线重连 | 浏览器原生自动重连 | 需手动实现 |
| 实现成本 | 后端返回 Flux 即可 | 需要握手、会话管理 |

AI 答疑是"用户发一条、服务端流式回一条"的单向推送场景，SSE 完全够用且成本低得多；提问动作本身用普通 POST 完成。**技术选型匹配场景，而不是追新。**

### 规避的问题
- **多轮历史截断**：只携带最近 10 条历史进 prompt，防止对话过长超出模型上下文窗口、也控制 token 成本；
- **流内异常降级**：`onErrorResume` 捕获上游超时/异常，下发友好提示并落库，前端不会收到半截流后无响应；
- **前端缓冲区处理**：网络分包可能把一条 `data:` 切断，解析时把最后不完整的片段留在 buffer 等下次拼接，避免乱码丢字。

### 面试问答
**Q：SSE 和 WebSocket 你怎么选？**
A：看通信方向。AI 回答是服务端单向推送，SSE 基于 HTTP、自带重连、后端一个 Flux 搞定；WebSocket 双向能力在这里用不上，还要额外处理握手与会话管理，属于过度设计。

**Q：流式输出中途失败怎么办？**
A：三层兜底：上游 60 秒超时；`onErrorResume` 把异常转成友好文案下发并落库；前端 catch 后在气泡里显示"服务暂时不可用"。用户永远能看到一个确定的结果，而不是一直转圈。

## 4. AI 答疑：Prompt 工程与会话管理

### 怎么使用
- **System Prompt 分层组装**：基础人设（专业 AI 助教、回答要求）+ 课程上下文（动态注入课程标题与简介，要求围绕该课程答疑）；
- **会话模型**：`ai_chat_session`（会话，可关联课程）+ `ai_chat_message`（消息，role=user/assistant）；首次提问自动建会话，标题取问题前 30 字；
- **多轮历史**：按会话 ID 倒序取最近 10 条再反转为正序，组装成 `[{role, content}]` 传给模型。

### 解决什么问题
- 课程上下文注入让回答"有的放矢"：问"循环怎么用"，绑定了 Java 课程的会话得到 Java 示例，而不是泛泛而谈；
- 会话持久化让学生随时回顾历史问答，也符合真实客服/助教产品的交互形态。

### 规避的问题
- 会话归属校验：查看/删除会话前校验 `student_id` 匹配，防止学生 A 看到学生 B 的对话（水平越权）；
- 未配置 API Key 时不报错崩溃，而是返回明确的降级文案，**功能开关与配置缺失对主流程无侵入**。

## 5. AI 出题：结构化输出 + 教师审核入库

### 怎么使用
- **Prompt 约束 JSON 输出**：System Prompt 明确要求"只输出合法 JSON 数组，不要解释、不要 markdown 标记"，并给出每题的字段模板；
- **解析容错**：`stripCodeFence` 先剥掉模型可能违规输出的 ``` 代码块标记，再用 Jackson 解析；逐题校验题干与答案非空，过滤无效项；
- **两段式入库**：AI 生成 → 返回草稿（不入库）→ 教师在前端可编辑题干/选项/答案/解析 → 勾选后调 `save-drafts` 批量入库，`source=2` 标记 AI 来源。

### 解决什么问题
- 大模型自由文本输出不可直接入库，**"生成草稿 + 人工审核"两段式设计**把 AI 定位为"辅助"而非"替代"，保证题库质量底线；
- `source` 字段区分人工题与 AI 题，后续可统计 AI 出题占比、对比两类题目的错误率。

### 规避的问题
- 题型约束：AI 出题仅支持单选/多选/判断（答案可结构化校验），简答题参考答案主观性强，不适合自动生成；
- JSON 解析失败有明确兜底（"AI 返回格式异常，请重试"），不会把半截 JSON 写进数据库；
- 入库前再次校验章节归属课程，与人工录题同一套数据边界规则。

### 面试问答
**Q：大模型输出不稳定（不按 JSON 格式）怎么办？**
A：三层应对：① Prompt 里给明确的格式模板和负面约束（不要 markdown）；② 解析前剥代码块标记、解析后逐字段校验过滤；③ 解析彻底失败时返回可重试的业务提示。生产上还可以用 temperature=0、few-shot 示例或模型的 JSON Mode 进一步提高稳定性。

**Q：为什么 AI 生成的题目不直接入库？**
A：教育内容错误成本高（错误答案会误导学生），且大模型存在幻觉。人工审核是质量闸门，这也是"AI 辅助、人做决策"的产品原则体现。

## 6. AI 批改：评分 + 总分重算闭环

### 怎么使用
- **触发点**：考试交卷时简答题 `correct=0` 占位、`ai_score` 留空；教师端"待批改列表"查出所有 `ai_score IS NULL` 的简答题；
- **批改**：把题目、参考答案、学生答案组装成 prompt，要求模型输出 `{"score":8.5,"comment":"..."}`，解析后回写 `exam_answer` 的 `ai_score`/`ai_comment`；
- **总分重算**：`(客观题答对数 + Σ简答题得分/10) / 总题数 × 100`，更新 `exam_record.score`；
- **教师改分**：`adjust` 接口允许教师覆盖 AI 评分（0-10 校验），改分后同样触发总分重算。

### 解决什么问题
- 简答题无法规则判分，是阶段三遗留的缺口，AI 批改把考试判分闭环补全；
- "教师可采纳/改分"保留了人的最终裁决权，AI 评分只是初稿——与出题模块一致的"AI 辅助"理念。

### 规避的问题
- 评分范围双重校验：解析时校验 0-10，改分接口再校验一次，防止模型幻觉输出异常分数污染成绩；
- 总分重算放在事务内，批改回写与成绩更新要么全成要么全回滚，避免"批改了但成绩没变"的不一致；
- 待批改列表按教师名下课程过滤，教师只能批改自己课程的试卷。

### 面试问答
**Q：AI 打分不公平怎么办？**
A：这是已知局限，设计上用三点缓解：① prompt 要求按参考答案要点给分并输出理由（可解释）；② 教师可逐题改分，AI 只是初评；③ 论文展望中可引入多次评分取平均、或 rubric 评分量表细化标准。

## 7. 降级策略总览（贯穿全阶段）

| 异常场景 | 降级行为 |
|---------|---------|
| 未配置 ZHIPU_API_KEY | 答疑返回配置提示文案；出题/批改返回明确业务异常 |
| 大模型超时（60s/90s） | Reactor timeout 抛出，`onErrorResume` 转友好提示 |
| 上游返回格式异常 | 解析失败返回"请重试"，不写入脏数据 |
| 流式中途断流 | 已输出内容保留在气泡，前端 catch 提示 |

**设计原则：AI 是增值功能，任何 AI 异常都不能阻断登录、学习、考试等主业务。**

## 8. 面试问答要点（本阶段高频）

**Q：这个项目 AI 体现在哪里？**
A：三个落地场景：学生端 AI 答疑（SSE 流式、多轮对话、课程上下文）、教师端 AI 出题（结构化生成 + 审核入库）、AI 批改（简答题评分 + 总分重算）。都遵循"AI 辅助、人做决策"原则。

**Q：SSE 的实现细节？**
A：后端 Controller 返回 `Flux<String>`，Spring 编码为 `text/event-stream`；上游大模型同样是 SSE，用 WebClient 的 `bodyToFlux` 消费后透传，实现"上游流 → 后端流 → 前端流"的全链路流式。前端用 fetch + ReadableStream 解析，因为 axios 不支持流式读取。

**Q：如何控制大模型调用成本与稳定性？**
A：多轮历史截断最近 10 条控制 token；流式/非流式分别设超时；出题用非流式（需要完整 JSON），答疑用流式（体验优先）——按场景选择调用模式。

**Q：如果让你优化 AI 答疑，下一步做什么？**
A：① RAG：把课程讲义向量化，答疑时检索相关段落注入 prompt，减少幻觉；② 敏感词与内容安全过滤；③ 对话评价（点赞/点踩）回流优化 prompt。
