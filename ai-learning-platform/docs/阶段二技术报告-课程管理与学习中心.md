## 2. 三级内容结构：课程 → 章节 → 视频

### 怎么使用
- 三张表 `course` / `chapter` / `video` 通过 `course_id`、`chapter_id` 逐级关联，均带 `sort_order` 字段支持自定义排序；
- 教师保存课程时，前端把"章节 + 视频"整棵树作为嵌套 JSON 一次性提交（`CourseSaveDTO`），后端在一个事务内完成增删改。

### 解决什么问题
- 在线学习平台的内容天然是层级结构，三级建模让"章节目录、按章练习、进度统计"都有明确挂载点；
- 整树提交 + 事务保证了"编辑课程结构"的原子性——不会出现章节保存成功、视频保存一半的脏数据。

### 关键算法：树的差量同步
保存章节/视频时采用"**按 id 更新、无 id 新增、列表中不存在的删除**"策略：
1. 遍历提交的列表，有 id 的执行 update 并记入保留集合，无 id 的执行 insert；
2. 查出数据库中该课程的全部旧章节，凡不在保留集合中的，连同其视频一并删除。

### 规避的问题
- 如果采用"先全删再全插"的粗暴方案：主键 ID 会变化，导致已关联的学习记录、题目、评论全部失联；差量同步保住了 ID 稳定性。
- 删除课程前校验"是否有学生选课"，避免级联删除破坏学习数据。

## 3. 课程审核状态机

### 怎么使用
- `course.status` 三态：`0 待审核 → 1 已上架 / 2 已下架（驳回）`；
- 教师每次编辑已上架课程后状态自动回落到"待审核"，需重新提交；
- 管理员审核接口校验"课程必须处于待审核状态"，防止重复审核。

### 解决什么问题
- UGC 内容（教师上传的课程）必须有审核闸门，否则平台可能出现违规内容；
- 状态机让"谁能看、谁能改"有明确依据：学生端广场只查 `status=1`，未上架课程仅授课教师与管理员可预览。

### 不用的后果
- 没有审核流，任何教师注册后即可向全站学生发布内容，平台内容质量与安全不可控，这在毕业答辩中是明显的业务漏洞。

## 4. 学习进度体系：上报 → 完课 → 完成度重算

### 怎么使用
- **进度上报**：学生端播放视频时周期性调用 `/study/progress`，上报 `videoId + position`；
- **完课判定**（双通道）：前端显式上报 `finished=true`，或后端检测 `position >= duration × 95%` 自动判定——两个条件任一满足即标记完课；
- **断点续播**：`/study/resume/{videoId}` 返回上次播放位置，播放器 seek 到该位置；
- **完成度重算**：首次完课时触发 `已完成视频数 / 视频总数 × 100`，写入选课表 `progress` 字段。

### 解决什么问题
- 95% 阈值解决了"用户拖到最后 1 秒算不算看完"的边界争议，同时容忍片尾几秒的误差；
- 完成度冗余存储在选择课表（而非每次实时统计），列表页查询无需聚合计算，**以空间换时间**。

### 规避的问题
- 完课标记做了**幂等处理**：只有 `finished` 从 0 变 1 的那一次才触发完成度重算，避免重复上报导致重复计算（阶段五的积分奖励也依赖这个"首次完课"信号，防止刷积分）。
- 如果进度只存前端 localStorage：换设备/清缓存进度全丢；存后端才是可靠方案。

### 事务边界
进度上报方法标注 `@Transactional`，"更新播放位置 + 标记完课 + 重算完成度"三步要么全成要么全回滚，避免进度数据不一致。

## 5. 查询性能处理：批量查询代替循环单查

### 怎么使用
- 组装"章节视频树"时：先一次查出课程下所有章节，再用 `IN (chapterIds)` 一次查出全部视频，内存中用 `Collectors.groupingBy` 按章节分组；
- 学习记录同理，一次 `IN` 查询后转成 `Map<videoId, record>`。

### 解决什么问题
- 避免经典的 **N+1 查询问题**：若在循环里逐个章节查视频，一门 10 章的课就是 1 + 10 次 SQL；改为批量后固定 2~3 次 SQL。

### 面试问答要点
**Q：你的课程详情页是怎么避免 N+1 的？**
A：三级数据分三次批量查询（课程 → 章节 IN → 视频 IN），在内存中用 Map 分组组装树，SQL 次数与章节数量无关。

## 6. 前端实现要点

### 课程管理页（Ant Design Vue）
- 使用 `a-drawer` 抽屉承载"课程 + 章节 + 视频"的嵌套表单，动态增删行；
- 提交前本地组装树结构，一次请求完成整树保存。

### 学习中心（Naive UI）
- `<video>` 原生播放器 + `timeupdate` 事件节流上报进度；
- 进入播放前先请求断点续播接口，`loadedmetadata` 后 seek；
- 章节目录用折叠面板展示，已完课视频打勾标识。

### 规避的问题
- 进度上报做了节流（不是每秒都发请求），降低后端压力；
- 如果视频播放不做任何鉴权，未选课用户可直接拼 URL 看视频——本项目通过学习页路由守卫 + 后端接口登录态控制访问。

## 7. 面试问答要点（本阶段）

**Q：课程进度为什么存在选课表而不是每次实时算？**
A：实时算需要"查章节 → 查视频 → 聚合学习记录"多次查询，列表页每门课都算一遍代价太高；完课时重算一次并冗余存储，读多写少场景下这是典型的空间换时间。

**Q：编辑课程结构如何保证数据一致性？**
A：整树差量同步 + `@Transactional` 事务：有 id 更新、无 id 新增、消失的删除；任何一步失败整体回滚。同时保留原主键，避免关联数据（学习记录、题目）失联。

**Q：完课判定为什么是 95% 而不是 100%？**
A：视频末尾常有黑帧/片尾，浏览器 `ended` 事件在部分场景不触发；95% 是兼顾准确性与容错的经验阈值，同时保留前端显式上报作为兜底。

**Q：如何防止学生刷完课进度？**
A：完课标记幂等（只在 0→1 时生效），积分奖励绑定"首次完课"信号；后续阶段还可在上报接口校验播放时长合理性。
