# 阶段五技术报告：积分系统与管理端运营

## 2. 积分账户模型：一人一户 + 三字段记账

### 怎么使用
- `points_account` 表：`user_id` 唯一索引保证一人一户；同时维护 `balance`（当前余额）、`total_earned`（累计获得）、`total_spent`（累计消耗）三个字段；
- 账户懒创建：查询/发放时若不存在则自动建户（余额 0），避免注册流程强依赖积分表；
- 每笔变动同步写 `points_record` 明细（类型/变动值/说明/时间），余额与明细互为印证。

### 为什么这样设计
- **为什么不只存一个 balance**：余额只能回答"现在有多少"，回答不了"赚了多少、花了多少"。三字段记账让个人中心一次查询就能展示完整资产视图，也便于后续做统计看板；
- **为什么明细表不做外键关联账户**：明细按 `user_id + create_time` 建联合索引即可满足"我的明细"分页查询，省掉 join，符合读多写少的查询模式。

### 规避的问题
- 余额、累计获得、累计消耗在同一事务内同步更新，避免只改余额不记明细（或反之）造成的账实不符；
- 明细 `change_value` 正负号约定（正为获得、负为消耗），前端直接按符号着色，无需额外字段。

## 3. 防超扣：条件 UPDATE 代替"先查后扣"

### 怎么使用
扣积分不走"查余额 → 判断 → update"三步，而是一条条件 SQL：

```sql
UPDATE points_account
SET balance = balance - #{cost}, total_spent = total_spent + #{cost}
WHERE user_id = #{userId} AND balance >= #{cost}
```

返回受影响行数：为 0 说明余额不足，抛业务异常回滚整个兑换事务。

### 解决什么问题
"先查后扣"存在经典竞态：两个请求同时查到余额 800，各自认为够扣 800，最终扣成 -800（透支）。条件 UPDATE 把"判断 + 扣减"合并为数据库内一条原子语句，InnoDB 行锁保证并发执行时串行化，**天然杜绝超扣**，无需引入分布式锁或乐观锁版本号。

### 面试问答
**Q：并发扣积分怎么防止透支？**
A：核心是把校验和扣减合并成一条带条件的 UPDATE（`WHERE balance >= cost`），利用数据库行锁保证原子性；返回行数为 0 即余额不足。相比"先查后扣"消除了 check-then-act 竞态；相比乐观锁（version 字段）不需要重试循环，代码更简单。若未来是跨库账户，再考虑分布式锁或 TCC。

**Q：为什么不用乐观锁？**
A：乐观锁适合冲突率低的更新场景，需要额外的 version 字段和失败重试逻辑。本场景一条条件 UPDATE 就能原子完成，是"够用且最简"的方案。

## 4. 兑换一致性：单事务闭环 + 防重复兑换

### 怎么使用
`ExchangeService.exchange()` 在同一个 `@Transactional` 内完成四步：
1. 校验课程已上架且为积分定价；
2. 查兑换记录防重复（已成功兑换过的课程不允许再扣积分）；
3. 条件 UPDATE 扣积分（余额不足抛异常 → 全部回滚）；
4. 自动选课（复用 `EnrollmentService.doEnroll`，幂等）+ 写兑换流水。

### 解决什么问题
- **原子性**：扣积分成功但选课失败时，事务回滚保证积分不被"白扣"；反之亦然；
- **防重复消费**：先查兑换流水再扣积分，避免学生对同一门课反复点击导致多次扣积分；
- **选课幂等**：`doEnroll` 内部先查已有选课记录，存在则直接返回，兜底一切异常重试场景。

### 规避的问题
- 课程下架/改价后仍可兑换？——兑换时实时读课程状态与当前定价，不信任前端传来的价格；
- 兑换失败也留痕：流水表 `status` 区分成功/失败，便于管理员排查争议。

### 面试问答
**Q：积分兑换课程如何保证数据一致？**
A：整个兑换流程放在一个数据库事务里：校验 → 扣积分（条件 UPDATE）→ 自动选课 → 写流水，任一步失败整体回滚。扣积分用带余额条件的 UPDATE 防并发超扣，选课服务本身幂等，重复兑换在前置查询就被拦截。单库单服务内用本地事务即可，不需要分布式事务的复杂度。

## 5. 积分发放：规则驱动 + 每日上限 + 幂等

### 怎么使用
- **规则表驱动**：所有奖励值、每日上限、启停都存 `points_rule`（video_finish / daily_sign / exam_pass / ai_ask / register_gift），管理员后台可在线调整，**改配置不发版**；
- **统一发放入口**：`PointsService.grantByRule(userId, ruleKey, desc)`——规则停用或奖励值为 0 时静默跳过（返回 false），不阻断主业务；
- **每日上限**：发放前统计"当日该类型已发放总额"，达到 `daily_limit` 即拒绝，防刷分；
- **幂等发放**：`grantOnceByRule` 按"类型 + 说明中的唯一标记"查重，典型用于考试及格奖励（标记 `exam#{examId}`）。

### 五大触发点接入方式

| 触发点 | 接入位置 | 幂等/防刷手段 |
|--------|---------|--------------|
| 完课 +10 | `StudyService.reportProgress` 首次完课分支 | 仅 `firstFinish=true` 触发一次 |
| 签到 +5 | `SignService.sign` | `(user_id, sign_date)` 唯一索引 + DuplicateKey 兜底 |
| 考试及格 +20 | 交卷判分后 + AI 批改重算后 | `exam#id` 标记去重，两处触发只发一次 |
| AI 提问 +2 | 流式回答 `doOnComplete` 后 | 回答成功才发 + 每日上限 10 |
| 注册赠送 +100 | 注册事务内 | 注册本身唯一 |

### 解决什么问题
- **及格奖励的两处触发**：交卷时简答题记 0 分可能不及格，AI 批改后重算分数可能跨过及格线——两个位置都调用 `grantOnceByRule`，靠 `exam#id` 标记保证只发一次，不漏发也不重复发；
- **防刷分**：AI 提问奖励只在流式回答成功完成后发放，且每日上限 10 积分，脚本刷接口无利可图；
- **运营灵活性**：奖励值调整、活动开关都不需要改代码重启。

### 面试问答
**Q：积分奖励怎么防止重复发放？**
A：分场景处理。行为本身唯一的（签到）靠数据库唯一索引；业务上可能多次触发的（考试及格在交卷和 AI 批改重算时都可能达到）用"幂等标记"——明细说明里写入 `exam#123`，发放前先按类型+标记查重。本质是给每笔"应得的奖励"一个业务唯一键。

**Q：为什么奖励规则放数据库而不是配置文件？**
A：配置文件改了要重启，且运营人员改不了。规则表 + 管理后台让运营可以即时调整活动力度（如考试周双倍积分），这是"配置数据化"的常见思路。

## 6. 每日签到：唯一索引兜底并发

### 怎么使用
- `sign_record` 表 `(user_id, sign_date)` 唯一索引；
- 签到流程：先查今日是否已签（给用户友好提示）→ 插入记录 → 捕获 `DuplicateKeyException` 兜底（并发双击场景）→ 发放签到积分。

### 解决什么问题
前端按钮连点、两个标签页同时签到等并发场景下，"先查后插"可能插入两条记录。唯一索引是最后一道防线，数据库层面保证一人一天一条，应用层捕获重复键异常转为友好提示。

### 面试问答
**Q：签到接口如何保证一天只能签一次？**
A：双层保障。应用层先查询当日记录给出友好提示；数据库层 `(user_id, sign_date)` 唯一索引兜底，并发插入时捕获 DuplicateKeyException。查询是体验优化，唯一索引才是正确性保证——不能只靠应用层判断。

## 7. 运营模块：公告/评论/用户管理

### 公告：发布-撤回状态机
- 状态字段 `0已撤回 1已发布` + `top` 置顶标记；学生端只查已发布公告（置顶优先、时间倒序），管理端可全量管理；
- 撤回而非删除：运营误操作可恢复，也保留历史记录。

### 评论：先审后发
- 学生评论默认 `status=0 待审核`，管理员审核通过（1）才在课程详情页展示，违规可隐藏（2）或删除；
- 列表接口联表组装昵称/课程标题，管理端一屏看清"谁在哪门课说了什么"。

### 用户管理：自我保护
- 启用/禁用、角色调整前校验"不能操作自己"，防止管理员误操作把自己锁在系统外——这是后台系统常见的边界细节。

### 规避的问题
- 所有管理端接口入口统一 `UserContext.checkRole(ROLE_ADMIN)`，学生/教师无法越权调用运营接口；
- 评论与公告内容均做非空校验，避免空内容入库。

## 8. 前端实现要点

### 学生端（Vue 3 + Naive UI）
- **积分中心**：账户概览（余额/累计）+ 签到按钮（今日已签自动禁用）+ 明细表格（正负着色）+ 积分商城（已兑换课程按钮置灰）；
- **顶部积分实时显示**：MainLayout 挂载时拉取账户余额，点击直达积分中心；
- **课程详情页**：积分课程选课按钮跳转积分中心；新增评论区（发表评论 + 已审核评论列表）。

### 管理端（Vue 3 + Ant Design Vue）
- 公告管理（CRUD + 发布/撤回 + 置顶）、评论审核（展示/隐藏/删除）、积分规则（行内编辑奖励值/上限 + 启停开关）、兑换记录（按学生筛选）、用户管理（角色下拉调整 + 禁用确认）；
- 复用既有 `request.js` 拦截器：统一携带 token、统一解包 `{code, message, data}`、401 自动登出。

## 9. 本阶段踩坑与经验

| 问题 | 现象 | 解决 |
|------|------|------|
| 先查后扣竞态 | 并发兑换可能透支 | 条件 UPDATE（`balance >= cost`）+ 行锁 |
| 及格奖励重复发 | 交卷发一次、AI 批改重算又发一次 | `grantOnceByRule` 按 `exam#id` 标记查重 |
| 签到并发重复 | 双击产生两条记录 | 唯一索引 + DuplicateKeyException 兜底 |
| 积分发放阻断主业务 | 规则表异常导致完课接口报错 | 发放失败静默跳过（返回 false），不抛异常 |
| 管理员误禁用自己 | 后台被锁 | 操作前校验"不能修改自己" |

**核心经验**：涉及资产（积分/余额）的写操作，正确性保障要放在数据库层（唯一索引、条件 UPDATE、事务），应用层的判断只是体验优化；奖励发放要设计幂等键，任何"可能触发两次"的路径都要能安全去重。
