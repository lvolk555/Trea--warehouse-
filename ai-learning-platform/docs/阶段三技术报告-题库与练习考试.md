# 阶段三技术报告：题库与练习考试

> 本报告记录阶段三"练 → 考"链路的技术选型与实现细节，作为毕业答辩与面试复盘材料。

---

## 1. 本阶段功能回顾

| 模块 | 功能 |
|------|------|
| 题库管理 | 单选/多选/判断/简答四种题型录入，强制绑定课程 + 章节 |
| 章节练习 | 按章节随机抽客观题、单题即时判分、解析展示 |
| 组卷考试 | 教师勾选出题组卷、发布、学生限时考试、答题卡 |
| 自动判分 | 客观题自动判分、百分制成绩、答题明细 |
| 错题本 | 错题按课程归类、对比展示、标记掌握 |

## 2. 题目归属设计：课程 → 章节两级强制绑定

### 怎么使用
- `question` 表同时冗余 `course_id` 与 `chapter_id`，数据库建联合索引 `idx_course_chapter`；
- 保存题目时后端校验"章节必须属于所选课程"（查章节表比对 `course_id`），前端级联选择器同步约束；
- 组卷时逐题校验"题目必须属于试卷所选课程"。

### 解决什么问题
- 早期原型中题目与课程关联混乱（用户反馈"逻辑混乱"），两级强制绑定让"按章节练习、按课程出卷"都有确定数据范围；
- 冗余 `course_id` 是**有意的反范式**：按课程筛选题目时无需 join 章节表，一次索引扫描完成。

### 规避的问题
- 如果只存 `chapter_id` 不存 `course_id`：按课程查题目必须 `question JOIN chapter`，高频查询性能下降；
- 如果不做归属校验：教师可以把别的课程的题目组进自己试卷，数据边界失控。

## 3. 题型建模：一张表承载四种题型

### 怎么使用
- `type` 字段区分：1 单选、2 多选、3 判断、4 简答；
- 选项用 **JSON 字符串**存 `options` 列（如 `["选项一","选项二"]`），实体层用 Jackson `ObjectMapper` 序列化为 `List<String>`；
- 答案统一存 `answer` 字符串：单选存 `"A"`，多选存 `"AB"`，判断存 `"对"/"错"`，简答存参考答案文本。

### 解决什么问题
- 四种题型共用一张表，避免"每种题型一张表"带来的 4 套 CRUD 与组卷时的多表 union；
- JSON 存选项兼顾灵活性（选项数量 2~6 可变）与结构完整性。

### 权衡与面试问答
**Q：为什么选项用 JSON 而不是拆成选项表？**
A：选项永远随题目整体读写（不存在只查某个选项的场景），拆表会增加 join 与级联删除复杂度；MySQL 8 的 JSON 类型还能在需要时建虚拟列索引。这是"按访问模式建模"的取舍。

**Q：多选题答案为什么存 "AB" 而不是数组？**
A：判分时需要比对集合，字符串归一化（去分隔符、转大写、排序）后直接 equals 即可，存储与比对都最简单；前端多选组件的数组在提交前 `join('')` 转换。

## 4. 判分引擎：客观题规则判分

### 怎么使用
- 单选/判断：去空格后 `equalsIgnoreCase` 比对；
- 多选：归一化函数 `normalizeMulti` —— 去除 `,，、空格` 分隔符 → 转大写 → 字符排序，使 `"a,b"`、`"BA"`、`"AB"` 全部等价；
- 简答题：本阶段记 0 分占位，`exam_answer` 表预留 `ai_score`、`ai_comment` 字段，阶段四 AI 批改后回填。

### 解决什么问题
- 归一化解决了"学生答案格式差异导致误判"的经典问题（用户写 "A、B" 和 "AB" 都应判对）；
- 预留字段让阶段四接入 AI 批改时**无需改表结构**，体现渐进式设计。

### 规避的问题
- 判分逻辑在练习（`PracticeService`）与考试（`ExamService`）中各自调用同一规则，保证"练习判对错"与"考试判对错"标准一致；
- 交卷接口做了**重复提交校验**（查已交卷记录），防止前端重复点击或恶意请求产生两条成绩。

## 5. 考试流程设计：限时与防重复

### 怎么使用
- **限时**：试卷存 `duration`（分钟），学生进入考试时后端返回时长，**前端倒计时 + 到时自动交卷**；剩余 5 分钟倒计时变红提醒；
- **答题卡**：左侧题号网格实时反映已答/未答状态（有答案的题号高亮），支持跳题；
- **防重复进入**：`startExam` 与 `submit` 均校验"该生是否已有交卷记录"，已考过直接拒绝；
- **答案保密**：学生进入考试时返回的题目 VO 主动置空 `answer` 与 `analysis`，防止前端 F12 看到答案。

### 解决什么问题
- 倒计时放在前端是因为考试是"固定时长"而非"固定截止时刻"，前端实现最简单且体验好；
- 服务端隐藏答案是底线安全——**永远不能把正确答案下发到不可信客户端**。

### 权衡与面试问答
**Q：倒计时只在前端，学生改本地时间/断网怎么办？**
A：这是毕业设计的已知取舍。生产级方案是服务端记录开始时间，交卷时校验 `当前时间 - 开始时间 > duration` 则按自动交卷处理，并配合心跳检测。本项目在论文"展望"部分说明了该升级路径。

**Q：为什么不让后端定时强制收卷？**
A：需要为每个考生维护服务端定时任务（如延迟队列），复杂度显著上升；当前"前端倒计时 + 服务端防重复交卷"组合已满足教学演示场景。

## 6. 抽题与错题本

### 随机抽题
- 章节练习按 `chapter_id + 客观题型` 过滤，`ORDER BY RAND() LIMIT n` 随机抽取；
- 简答题不参与练习（练习无 AI 批改，判分无意义），只出现在考试中。

**Q：ORDER BY RAND() 有什么性能问题？**
A：它会对全表生成随机数再排序，数据量大时 O(n log n) 且无法走索引。题库单章节题目量在百级，完全可接受；若未来题目上万，可改为"先查 ID 列表，应用层随机取 N 个 ID 再批量查"。

### 错题本
- 练习答错即写入 `practice_record`（`correct=0`），错题本查询条件为 `学生 + 答错 + 未掌握`；
- 按课程归类在**应用层分组**（查出后按 `courseTitle` 聚合），避免复杂 SQL；
- "标记掌握"将 `mastered` 置 1，错题本查询即过滤掉——**软删除思想**，保留历史作答数据可追溯。

## 7. 成绩计算

- 百分制：`答对题数 / 总题数 × 100`，`BigDecimal` + `HALF_UP` 保留一位小数，避免浮点误差；
- 考试记录与答题明细两表：`exam_record` 存总分（列表页快查），`exam_answer` 存每题明细（详情页展开），读写分离的表结构设计。

## 8. 前端实现要点

### 管理端（Ant Design Vue）
- 题库页：课程 → 章节级联筛选，录入弹窗按题型动态切换表单（单选填字母、多选勾选、判断对错）；
- 组卷页：抽屉内先选课程加载候选题目，checkbox 勾选出题，实时显示已选题数。

### 学生端（Naive UI）
- 练习页：三步状态机（选章节 → 答题 → 结果），单题提交后立即显示对错与解析；
- 考试页：`setInterval` 倒计时、答题卡双向联动、交卷前确认弹窗（提示未答题数）；
- 多选题答案数组在提交前统一 `join('')` 转字符串，与后端判分格式对齐。

## 9. 面试问答要点（本阶段）

**Q：一张表存四种题型，会不会有字段冗余？**
A：会有（简答题没有选项，判断题选项固定），但相比四张表带来的组卷 union、分页统计复杂度，少量空列的存储代价可以忽略；这是"单表继承"模式在业务简单时的常见选择。

**Q：如何保证考试答案不泄露？**
A：三层防护：① 学生接口返回的题目 VO 置空答案与解析；② 判分在服务端完成，前端只提交答案；③ 交卷后才在结果页下发正确答案。

**Q：考试交卷的并发安全怎么考虑？**
A：提交前查询是否已有交卷记录（幂等校验）；若追求更强保证，可对 `(exam_id, student_id)` 建唯一索引，用数据库约束兜底防重。

**Q：错题本为什么用 mastered 标记而不是直接删除记录？**
A：保留作答历史可用于后续学情分析（如"某题错误率"统计）；软标记也让"误标掌握"可恢复，符合最小破坏原则。
